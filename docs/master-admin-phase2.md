# Phase 2 — Master Admin implementation and release boundary

Date: 18 October 2026. Continues Website draft #88 and Backend draft #91 on `codex/master-admin-v1`; no dependency branch was replaced or merged into main.

## Accounts and authorization

- `admin_policy.py` owns the six-role capability matrix: Super Admin (1), Website CMS Admin (2), Academic Admin (2), Content Admin (3), User Management Admin (1), read-only Security/Audit Admin (1). The initial ten-seat policy is data in each roster, not hard-coded identities. Server validates configured capacities and exactly ten seats.
- `/v1/control-center/accounts`: tenant-derived roster; invite; verified-identity acceptance; activate/deactivate/revoke; role change; invitation cancellation. Invitations reserve a seat for 24 hours. Stored email is a normalized hash; roster responses redact it. No password, shared account or privileged browser claim is used.
- Invitation IDs are opaque identifiers, not bearer credentials: acceptance additionally requires the exact verified Firebase email, a signed project-bound identity, MFA and authentication within five minutes. Acceptance provisions application membership for that individual Firebase identity. Firebase Google sign-in supplies the identity; no server endpoint creates real Firebase users or sends email. The UI provides an invitation ID for manual secure delivery.
- User Management Admin may invite non-privileged operational roles. Only Super Admin changes administrator roles/activation/revocation. Self-deactivation and changes to the sole Super Admin are blocked. Initial bootstrap and break-glass recovery require separately approved operator execution; no anonymous bootstrap endpoint or default credentials exist.
- Every privileged request rereads membership; disabled membership and revoked-before timestamps reject old sessions. Sensitive operations require recent MFA. A membership updateTime precondition is included in privileged write commits, closing a revocation/write race. Role/roster revisions prevent lost edits, duplicate invitations and seat oversubscription. Application access revocation does not disable the person's underlying Google/Firebase account or student login globally.
- Per-operator persistent daily request budget: 2,000 requests. Provider token signature/issuer/audience/subject checks are reused; verified email, MFA and authentication-age checks are added. Tenant is never accepted from the browser as an authorization decision.
- TOTP setup, challenge, factor selection and reauthentication use Firebase's SDK. Setup keys/codes stay in component memory and are cleared when account changes/cancel completes; they are never saved to application storage or audit logs. Enrollment alone does not bypass the signed MFA claim requirement.
- Firebase TOTP requires Identity Platform and enabled TOTP support: https://firebase.google.com/docs/auth/web/totp-mfa . Configuration has NOT been queried or changed. Authenticator tests use synthetic SDK doubles; real enrollment remains a staging gate.

## Legacy cutover and Notes

- Backend `ADMIN_V1_ENABLED` defaults false. Website `VITE_ADMIN_V1_ENABLED=true` selects the new capability-aware workspace instead of the broad legacy AdminPanel and prevents browser-generated report-card writes. These switches have not been enabled in any deployed environment.
- With backend V1 enabled, middleware protects all existing `/v1/admin/*`, Notes management, branding and Office conversion paths before legacy logic runs. Role checks and school resolution are server-owned. Office conversion requires notes capability; legacy branding points operators to approved CMS media.
- Existing Neon topic-mastery reporting has no proven tenant column/mapping. In V1 it returns 503 before querying any academic records. This is deliberately unavailable, not falsely certified tenant-safe. Reporting requires a separately reviewed tenant mapping.
- Notes reuses existing upload/edit/replace/preview/publish/unpublish/soft-delete/restore/history/recovery APIs. Requests use `control_tenants/{tenant}` parents selected from admin membership or the student's server-managed `control_users` membership. Content Admin edits; Super Admin publishes. Writes verify current membership atomically. Student users cannot select another tenant; server-owned membership must be provisioned through approved school onboarding before access.
- Existing unscoped Notes remain untouched. Moving/serving them through V1 requires an approved mapping/migration rehearsal. No records were moved or read from a real database. Legacy PDFs are available in V1 only for an explicitly configured `ADMIN_LEGACY_TENANT` matching the authenticated school; otherwise access fails closed.
- Candidate Firestore/Storage rules retain Phase-1 behavior until server-managed `control_policy/enforcement.enabled=true`. At cutover, broad legacy admin grants stop authorizing writes; browser-written marks and all new server-only collections remain denied. Browser admin-membership writes are denied even before cutover. Policy/rules/backend/frontend must be released together after staging proof; flags alone do not prove isolation.

## CMS and media

- Published menu labels/icons/order/visibility feed existing navigation; approved pages, sections, cards and banners render as escaped text. English/Hindi and immutable route mappings remain supported. Missing/invalid published config falls back to last validated configuration or existing defaults. Polling refreshes published content every 30 seconds.
- Full bounded draft tree: component type, parent, title/body, locale, icon, route, order, visibility and archive/recovery. Server rejects duplicates, orphans, cycles, unknown routes/icons and unexpected fields. Core admin/auth/legal actions are outside this registry.
- Existing approval/publish/rollback uses immutable version snapshots, optimistic revisions and atomic server audit. History paginates twenty snapshots. Restoring a published revision never deletes history or media.
- Tenant-scoped media supports validated PNG up to 2 MB and 2048px per side (8-bit RGB/RGBA, no interlace). CRCs/pixel stream are checked, metadata is stripped, private immutable objects are uploaded create-only, and pending metadata journals remain discoverable after failures. SVG/HTML/arbitrary URLs are not accepted. Existing PDF/DOCX support stays in Notes; this does not duplicate that API.
- Only media referenced by the current approved publication and an effectively visible tree node can be served publicly by the API. A hidden/archived parent revokes child image visibility. Hidden text is redacted from public config. Private storage is not made public.
- First version still lacks side-by-side draft diff/impact summary, a visual media library and abandoned-upload recovery UI. Notes recovery remains available. PNG is intentionally the only new raster upload format.

## Assessments

- `/v1/assessment/tests/{id}`: Academic/Super author server-owned objective keys and written rubrics with revision checks and immutable history. Students receive questions/options/marks only, never keys/rubrics.
- `/attempts/{id}`: authenticated school membership and owner-bound idempotency ID; server test revision; unknown-answer and extra-field rejection; deterministic objective scoring; AI input built from stored rubrics. Grades are validated and totals calculated by the server. Answers and test snapshots are stored privately, not in audit events.
- A single atomic admission creates pending state and consumes daily budgets (10/student, 1,000/school), with test-version precondition. Identical completed replay returns stored results with no inference/quota charge. Changed replay/cross-account access is denied. Pending/uncertain inference is never automatically repeated.
- Students retrieve their own results and appeal. Academic Admin reviews only attempts in their school and records bounded integer corrections with rationale, recent MFA, revision checks and immutable history. Self-review is blocked. No dedicated Assessment Admin role exists.
- Existing browser-reference-answer evaluation returns 410 when V1 is enabled. V1 UI routes evaluation/test-yourself to the server-owned test flow and prevents legacy browser scores being persisted.
- Uncertain/crashed pending evaluations require operator reconciliation; durable worker retry/reconciliation UI and a school-wide appeals queue are not implemented. Academic review currently opens an explicit attempt ID. No real model, GPU or student answer was used in verification.

- Frontend: 105 functional tests passed; TypeScript, ESLint and production build passed. Vite native-config and large bundle warnings persist. Some legacy esbuild fixture builds warn about import.meta; these are not suppressed.
- Four actual Chromium fixture tests passed: mobile 390px, tablet 768px, desktop 1440px and Audit role denial. Account invite/deactivate and CMS edit/save were exercised; axe WCAG A/AA reported zero violations in those fixtures. Firebase/MFA/HTTP responses are synthetic. Notes is stubbed in this browser harness. This is not real Firebase authentication, cloud media, Notes rendering or staging E2E.
- Initial browser run started before Chromium download finished and failed missing executable; rerun passed after installation. Initial npm audit had sandbox DNS failure; permitted rerun reported zero vulnerabilities. Local Firestore emulator attempt failed because Java was missing; CI installs Java and is the authoritative execution location for the new rules test. Windows asyncio requires permitted local socket support; no cloud calls are enabled by that permission.
- Browser dependencies are isolated/pinned in `tests/browser`, with a separate lock and credential-free CI job. Application production dependencies/locks remain unchanged.
